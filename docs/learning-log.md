# Learning log

What each phase taught, and what I should now be able to explain in an interview.

## Phase 1: Foundation

A safetensors file starts with an 8-byte length and a JSON header listing every tensor's dtype and shape, so a model's exact parameter count costs a few KB of HTTP range requests, not a weights download. Mixed-precision Adam keeps 16 bytes per parameter: a 2-byte weight and gradient, plus a 4-byte fp32 master copy and two 4-byte moments. ZeRO stages 1, 2 and 3 partition the optimizer states, then the gradients, then the weights across data-parallel ranks, and offload moves the optimizer (and at stage 3 the weights) to CPU RAM.

I should be able to explain: why fine-tuning a 7B model in mixed precision needs about 112 GB before activations, the per-GPU memory formula for each ZeRO stage, what optimizer offload saves on the GPU and costs in host RAM, how LoRA's r(in + out) parameters change which terms shrink, and why an HTTP client must drop the auth token on a cross-host redirect.

## Phase 2: Activations

Activation memory is the set of tensors autograd saves in the forward pass for backward, and each op saves only what its required gradients need: a frozen Linear keeps nothing for its weight, RoPE keeps only cos and sin, and LoRA therefore saves less than full fine-tuning. Fused SDPA keeps no s x s scores, while eager attention keeps an fp32 softmax and its copy. At large vocabularies the output head dominates: fp32 log-softmax plus its backward buffers come to 14 bytes per vocabulary entry per token in bf16, more than all layers of a small model together. Implementation details move memory too: whether transformers builds an explicit mask (sliding windows, padding) decides whether SDPA keeps an s x s bias and whether K/V get copied to every query head.

I should be able to explain: how to count a decoder layer's saved tensors from the modeling code, why logits and loss are often the largest allocation, what activation checkpointing keeps and where its peak is, why the training peak is the larger of the start of backward and the optimizer step's fp32 gradient copy, and how `torch.autograd.graph.saved_tensors_hooks` checks such a formula byte for byte.

## Phase 3: Calibration

Measuring 55 DeepSpeed runs on 2x T4 showed that the model-state formulas from the ZeRO paper are not what DeepSpeed allocates at the peak. Gradients don't exist at the start of backward (except ZeRO-3's preallocated partition), ZeRO-1 behaves like ZeRO-2 with gradient accumulation 1, the optimizer step makes temporary fp32 copies (8 bytes per parameter without ZeRO), and ZeRO-3 keeps a 0.93 GiB reduce bucket plus every parameter that comes back within `stage3_max_reuse_distance`. With those terms the allocated peak is within 2% on 33 of 35 runs. Reserved memory is a different problem: the caching allocator never returns segments, and DeepSpeed's init and per-step buffers leave holes of slightly wrong sizes, so reserved can exceed allocated by 1-3 GiB with no clean formula. The harness also taught me to check that a feature is really on: checkpointing was silently off because `from_pretrained` returns the model in eval mode, and the measured bytes were identical to the byte.

I should be able to explain: when in a training step memory peaks and what is alive at each moment, why ZeRO-1 measured the same as ZeRO-2, what ZeRO-3's reuse distance and reduce bucket cost, how PyTorch's caching allocator turns freed blocks into reserved-but-unused memory and how to read a `_record_memory_history` trace, why a fits verdict should use allocated memory, and why the 1.5B offload runs failed on host RAM rather than GPU memory.

## Phase 4: Recommendations and config generation

Choosing a setup turned out to be mostly about what the estimate can and can't promise. GPU memory has a measured error, so a recommendation needs that error as headroom: a setup that comes to 14.99 GiB on a 15 GiB card is not a safe pick. Host RAM has no calibrated formula, and the offload state FitCheck counts was half of what the T4 runs used, so it can only rule a setup out. Writing the config showed that the estimate rests on DeepSpeed defaults no config mentions: `overlap_comm` is on only at stage 3, `contiguous_gradients` decides whether ZeRO-1 keeps full gradients, and with fp32 gradient accumulation bf16 ZeRO-1 quietly switches to a different optimizer wrapper (`BF16_Optimizer`). Writing these out makes the config match the estimate even if a default changes, and DeepSpeed's own pydantic parser rejects any key it doesn't know, which makes it a cheap test. The T4 check of the picks also caught a formula I had only derived from source: gradient accumulation used 1 GiB more than predicted, so a source reading is a hypothesis until a run measures it. An allocator trace found the buffer in one pass: ZeRO-1 allocates its reduce bucket in the first gradient hook but frees it only at the accumulation boundary. To find a block in a trace that keeps only recent events, start from the blocks live at the end and replay the events backwards. The ZeRO-0 run also showed that fragmentation can cause an OOM: a 1.16 GiB request failed with 1.65 GiB reserved but unused, because PyTorch can only release segments that hold no live blocks.

I should be able to explain: why ZeRO-3 costs 1.5 times the communication of stages 1 and 2 and what optimizer offload moves over PCIe, why checkpointing costs about a third more compute, how DeepSpeed picks FusedAdam, DeepSpeedCPUAdam, `FP16_Optimizer` or `BF16_Optimizer` from the config, which ZeRO settings change the memory and which only change speed, and why a recommender should say "unknown" instead of guessing when part of the model isn't modeled.
